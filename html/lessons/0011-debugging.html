Debugging: when the browser lies to you

HTML has no syntax errors — and that's the trap. Browsers parse it permissively: badly-formed markup still renders something, fixed silently by rules you didn't choose. You get a page, but not necessarily your page.

~25 min · prereq: all prior

What the browser does with your mistakes

<p>I didn't expect to find the <em>next-door neighbor's <strong>cat</em></strong> here!</p>

Badly nested. The browser untangles it into

<em>next-door neighbor's <strong>cat</strong></em>

— but worse cases bite harder:

1
Unclosed <strong>

The browser can't guess where it ends, so it bolds the rest of the document — each block wrapped in its own strong element, to the bottom of the page.

2
Missing attribute quote

<a href="https://www.mozilla.org/>link</a> — the unterminated quote swallows the tag, and the browser deletes the link entirely. The most invisible failure in HTML.

3
Unclosed <li>/<p>

Usually guessed correctly — that's why the habit forms. Then you meet a case where the guess is wrong and spend an hour.

Tool 1: the DOM inspector

The devtools Inspector/Elements tab shows the rendered DOM — not your source, but what the browser made of it. Open devtools (F12 / right-click → Inspect), expand nodes, hover to highlight in the viewport. When something looks wrong, the first question is: what did the browser actually build?

Tool 2: the W3C validator

Paste your document into validator.w3.org (Direct Input tab) and press Check. Interpreting the messages:

  • "End tag li implied, but there were open elements" — a missing close tag.
  • "Unclosed element strong" — exactly what it says.
  • "End of file reached when inside an attribute value" — cryptic, but it means an unterminated quote swallowed the rest of the document.

One broken tag can cascade into a dozen errors — fix the first few, revalidate, repeat. You're done when the green banner appears: "Document checking completed. No errors or warnings to show." Aim for that banner on everything you ship — including every exercise in this course.

Exercise — the real MDN task (Debugging HTML)

This document has three planted bugs. Run it in a browser, inspect the rendered DOM to see what the browser built, then validate it and fix everything:

<!doctype html>
<html lang="en-US">
  <head>
    <meta charset="utf-8">
    <title>HTML debugging examples</title>
  </head>

  <body>
    <h1>HTML debugging examples</h1>
    <p>What causes errors in HTML?
    <ul>
      <li>Unclosed elements: If an element is <strong>not closed properly,then
          its effect can spread to areas you didn't intend
      <li>Badly nested elements: Nesting elements properly is also very important
          for code behaving correctly. <strong>strong <em>strong emphasized?</strong>
          what is this?</em>
      <li>Unclosed attributes: Another common source of HTML problems. Let's look
          at an example: <a href="https://www.mozilla.org/>link to Mozilla homepage</a>
    </ul>
  </body>
</html>
Show the fixes 
Close the <p> after "in HTML?" — close each <li> — close the first <strong>
after "properly," — untangle the strong/em nesting — and put the closing
double-quote back on the href:

<a href="https://www.mozilla.org/">link to Mozilla homepage</a>
