TCP: the three-way handshake

You already know the sequence: SYN → SYN-ACK → ACK. Interviews don't stop there. The killer follow-up is "why three packets — wouldn't two be enough?" That's this lesson's one thing: understanding what the handshake actually negotiates.

What TCP promises you

  • Reliable — lost segments get retransmitted.
  • Ordered — bytes arrive in send-order, even if packets take different paths.
  • Flow control — the receiver won't be flooded beyond its buffer.
  • Congestion control — the sender backs off when the network is struggling.

All of that needs one thing before any data flows: both sides agreeing on where the byte stream starts. That agreement is the handshake.

The handshake, on the wire

client → server : SYN, seq=x
server → client : SYN+ACK, seq=y, ack=x+1
client → server : ACK, ack=y+1
1
SYN

Client picks a random starting sequence number x and sends it. "I want to talk; I'll count my bytes from x."

2
SYN-ACK

Server replies with its own starting number y, plus ack=x+1 — "got your x; everything up to x is confirmed."

3
ACK

Client confirms y: "got your y." Both directions are now open with agreed starting points. Data flows.

Why not two?

The classic trap answer: "to establish the connection." The real reason: each side must hear its own sequence number acknowledged. After two packets the client knows the server got x, but the server has no confirmation that the client received y. Without that third packet, an old duplicate SYN arriving late could make a half-open connection the server thinks is live. Three packets = both directions proven, both ISNs locked in.

Closing down

Symmetric teardown: side sends FIN, other side ACKs, then sends its own FIN, first side ACKs back. Four packets because each direction closes independently — you can stop sending while still receiving.

TCP vs UDP — when you skip all of this

UDP is TCP's no-guarantees sibling: no handshake, no ordering, no retransmission — just fire the datagram. That's not "worse", it's a different deal:

TCPUDP
Connectionhandshake firstnone — just send
Deliveryguaranteed, orderedbest-effort, may drop/reorder
Speed to first byte≥ 1 RTT for handshake0 RTT
Used byHTTP/1.1, HTTP/2, SSH, emailDNS queries, video calls, gaming, QUIC/HTTP/3

Interview heuristic: if a late packet is worse than a lost packet, use UDP. A retransmitted video frame from three seconds ago is useless; a DNS query is one tiny request-response where a handshake would double the cost.

The real skill: say it out loud

Two prompts, 30 seconds each, out loud:

  1. "Walk me through the TCP handshake."
  2. "Why wouldn't two packets be enough?" — this is where candidates freeze.
Model answers (peek only after trying)

Handshake: "The client sends SYN with its initial sequence number x. The server responds SYN-ACK with its own starting number y and ack x+1. The client ACKs y+1. Now both directions have agreed starting points and are open."

Why not two: "After two packets the server has acknowledged the client's ISN but has no proof the client ever got the server's sequence number. A stale duplicate SYN could leave a half-open connection the server thinks is live. The third packet closes that loop — both ISNs are confirmed in both directions."
