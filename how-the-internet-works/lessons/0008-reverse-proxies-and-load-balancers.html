The server side: reverse proxies, load balancers, and one domain, many machines

Every chapter so far drew the server as one box that answers. But a real site gets millions of visits: no single machine has the CPU, memory, or connections for that — and even the world's biggest server would still be one box that can die, taking the site with it. The interview core of this chapter: "how does one domain name serve millions of users at once?"

Why one server is never enough

You can scale vertically — buy a bigger machine. It works until the ceiling: there's always a biggest machine, and it's still a single point of failure. So real systems scale horizontally: many ordinary servers, any of which can answer. That immediately creates a new problem — who decides which of the fifty servers gets your request?

The reverse proxy: one front door

A reverse proxy is a server that sits in front of your web servers and intercepts every client request, forwarding it to the right backend and returning its response. Clients only ever see the proxy — the origin servers stay hidden behind it. It's called reverse to contrast with the forward proxy (VPN, corporate web filter), which sits in front of clients and hides them from servers:

forward proxy: clients ─→ proxy ─→ internet (hides the CLIENTS)
reverse proxy: internet ─→ proxy ─→ app servers (hides the SERVERS)

Because everything passes through it, the reverse proxy is the natural place to bolt on shared concerns:

  • Hide the origins — attackers never learn the real server IPs, making targeted DDoS much harder.
  • TLS termination — the proxy handles the expensive encrypt/decrypt work and the certificates; app servers speak plain HTTP to it.
  • Caching and compression — lessons 0007's levers, applied once at the edge for everyone.
  • Load balancing — the big one, next.

Load balancing: spreading the requests

A load balancer is a reverse proxy whose job is spreading traffic across a pool of interchangeable servers. For each request it picks a server using an algorithm:

AlgorithmIdeaWhen it matters
Round robinNext request goes to the next server in the list.The default — dead simple, even spread.
Least connectionsSend to whichever server is currently least busy.Requests with uneven cost (long-lived connections).
Hash-basedHash the client IP (or URL) so the same client lands on the same server."Sticky sessions" — when a server holds per-client state.

The balancer also health-checks the pool constantly. A server that stops answering correctly is pulled out of rotation automatically — traffic flows around it to the healthy ones and the site stays up. That's failover, and it's the real reason for horizontal scaling: losing one machine becomes a non-event instead of an outage.

The statelessness catch interviews probe

Load balancing exposes a design assumption: any server might get your next request. If your shopping cart lives in server A's memory and your next click lands on server B, the cart is gone. Two fixes:

  • Sticky sessions — hash-based routing pins you to server A. Works, but fragile: if A dies your session dies, and load spreads unevenly.
  • Shared session store — keep state in Redis/PostgreSQL/a cookie, not in server memory, so any server can serve any request. This is the answer that scales, and why interviewers say "stateless services scale horizontally."

The real skill: say it out loud

  1. "How does one domain name serve millions of users at the same time?" — 45 seconds.
  2. "Forward proxy vs reverse proxy — and name two jobs a reverse proxy does for you."
Model answers (peek only after trying)

One domain, millions of users: "The domain resolves to a public entry point — a reverse proxy acting as a load balancer — not to any single server. It spreads incoming requests across a pool of identical app servers using something like round robin or least-connections. It health-checks every server and automatically stops sending traffic to one that fails, so losing a machine is a non-event. Scaling up means adding more servers behind the balancer. For that to work the servers have to be stateless — session state lives in a shared store, not in server memory, so any server can take any request."

Proxies: "A forward proxy sits in front of clients and hides them — a VPN or a corporate web filter. A reverse proxy sits in front of servers and hides them — clients never talk to the origins directly. Two jobs it does for you: TLS termination, so certificates and crypto live in one layer and app servers speak plain HTTP to it; and load balancing, spreading requests across the pool. It also commonly hides origin IPs for security and caches responses at the edge."
