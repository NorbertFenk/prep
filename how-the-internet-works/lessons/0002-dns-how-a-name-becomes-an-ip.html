DNS: how a name becomes an IP address

Last lesson, step 2 was a black box called "DNS lookup". Interviews open that box: "walk me through a DNS resolution." By the end you'll answer it cleanly, plus the follow-ups: CNAME vs A record? Why does DNS use UDP? Why do changes propagate slowly?

The cast

Four servers can be involved when nothing is cached:

R
Recursive resolver

Your delegate — usually your ISP's (or 8.8.8.8 / 1.1.1.1). It does the legwork on your behalf and caches answers.

.
Root nameserver

Doesn't know any IPs. Only knows: "for .com, ask these TLD servers."

T
TLD nameserver

Owns all of .com. Knows: "for example.com, ask its authoritative nameserver."

A
Authoritative nameserver

Holds the domain's actual records. Gives the final answer: the A record with the IP. End of the chain.

The lookup, step by step

1
Check the caches first

Browser cache → OS resolver cache → recursive resolver's cache. Any hit ends the journey here — most lookups never leave the resolver.

2
Resolver → root

"Where do I find .com?" Root replies with the TLD servers for .com.

3
Resolver → TLD

"Where's example.com?" TLD replies with the domain's authoritative nameservers.

4
Resolver → authoritative

"What's the A record for example.com?" It answers with the IP.

5
Answer travels back — and gets cached

The resolver returns the IP to your browser and stores it for the record's TTL. Next visitor with the same question is served from cache.

Interview follow-ups you now can handle

  • "Why does DNS use UDP?" — One small question, one small answer: no connection setup, no handshake overhead. If the response is too big for one packet (or gets lost), it falls back to TCP. Modern note: DNS-over-HTTPS and QUIC are changing this story.
  • "What happens if the resolver can't answer?" — It iterates: root → TLD → authoritative, exactly as above.
  • "Why so many caches?" — Each layer (browser, OS, resolver) short-circuits the trip. TTL controls how stale a cached answer may get.

The real skill: say it out loud

45-second timer, out loud: "Walk me through what happens when a browser resolves example.com."

Model answer (peek only after trying)

"The browser checks its own cache first, then the OS's — usually it stops there because resolvers cache aggressively. On a cold lookup, my query goes to a recursive resolver — my ISP's or something like 1.1.1.1. The resolver asks a root nameserver, which doesn't know IPs but refers it to the .com TLD servers. The TLD points at example.com's authoritative nameserver, which actually holds the records and returns the A record with the IP. The resolver hands me the IP and caches everything along that chain for the TTL, so the next lookup for that domain never leaves the cache."
