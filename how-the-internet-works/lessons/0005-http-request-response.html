HTTP: the request/response pair that carries the web

Last chapter ended with an encrypted TLS tunnel to the server. So what finally travels through it? HTTP — a plain-text protocol with exactly one pattern: the client sends a request, the server sends a response. Nothing else. It's also stateless: the server forgets you the moment the response is sent. The interview core: what's inside a request and a response, and how do methods, status codes and cookies fit in?

The request, on the wire

client → server : GET /search?q=tcp HTTP/1.1 ← request line: method + path + version
Host: www.google.com ← which site (one server hosts many)
Cookie: session=abc123 ← state the server set earlier
Accept: text/html ← what I can handle
(blank line, then the body — empty for GET)
PartWhat it says
Request lineMethod (what to do) + path (to which resource) + HTTP version.
HeadersName: value metadata — host, cookies, accepted formats, cache hints.
Blank lineMarks the end of headers. Everything after is the body.
BodyThe payload. Empty for GET; carries form data or JSON for POST/PUT.

The response, on the wire

server → client : HTTP/1.1 200 OK ← status line: version + code + reason
Content-Type: text/html; charset=UTF-8 ← what the body is
Set-Cookie: session=abc123 ← "remember this next time"
(blank line)
<!doctype html>…the actual page…

The status code is the server's one-word answer. Interviewers expect the classes cold:

ClassMeaningFamous examples
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirect — go somewhere else301 Moved Permanently, 302 Found
4xxClient error — your request is wrong400 Bad Request, 401 Unauthorized, 404 Not Found
5xxServer error — the request was fine, we broke500 Internal Server Error, 503 Service Unavailable

Methods: what you're asking for

MethodIntentBody?Idempotent?
GETRead this resourcenoyes — retrying is safe
POSTCreate / submit somethingyesno — retry may duplicate
PUTReplace this resourceyesyes — same result if repeated
DELETERemove this resourcenoyes — deleting twice is still deleted

Idempotent = repeating the request leaves the server in the same state. That's why a timed-out GET can be retried blindly but a timed-out POST ("charge my card?") must not be.

Bonus points interviewers love

  • Stateless → cookies. The server has no memory between requests. Set-Cookie hands the browser a token; the browser echoes it in a Cookie header on every later request. Sessions are this plus a database.
  • Connection reuse. One page needs ~100 requests. HTTP keep-alive reuses the same TCP+TLS connection; HTTP/2 multiplexes many requests over it at once — you don't pay the handshake per request.
  • Caching headers. Cache-Control tells browsers and CDNs how long a response stays fresh — that's why static assets load instantly on revisit.

Model answers (peek only after trying)

Request/response: "A request is a start line — method, path, HTTP version — plus headers like Host, Cookie and Accept, a blank line, and an optional body. The server answers with a status line — version, status code, reason — its own headers like Content-Type and Set-Cookie, a blank line, and the body: the HTML or JSON. Methods say what to do — GET reads, POST creates — and the status code class says how it went: 2xx success, 3xx redirect, 4xx my mistake, 5xx the server's mistake."

Stateless login: "HTTP has no memory — every request is standalone, the server forgets you after each response. Login works around that with cookies: after authenticating, the server sends Set-Cookie with a session token, and my browser attaches that Cookie header to every later request. The token is the only continuity; the server looks it up in its database to remember who I am."
