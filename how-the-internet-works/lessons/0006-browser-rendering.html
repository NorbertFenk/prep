Rendering: how the browser turns HTML into pixels

Last chapter ended with the server's response: 200 OK plus a body of HTML. That's just bytes. The browser now has to turn them into pixels — and it does it in a fixed sequence called the critical rendering path. The interview core: name the steps from bytes to pixels, and know what blocks them.

~15 min · builds on lesson 0005

The pipeline at a glance

HTML bytes → DOM (parse tags into a tree of nodes)
CSS bytes → CSSOM (parse styles — paint waits for this)
DOM + CSSOM → render tree (visible nodes only)
render tree → layout (exact position + size of everything)
layout → paint + composite → pixels on screen
1
HTML → DOM

The parser builds the Document Object Model as bytes arrive — it doesn't wait for the whole file. Every tag becomes a node in a tree. HTML is forgiving: broken markup gets fixed silently, you never get a syntax error.

2
CSS → CSSOM (render-blocking)

Styles are parsed into the CSS Object Model. The browser won't paint until it has them — better to wait a moment than paint wrong styles and redraw everything. The "cascade": when rules conflict, the most specific one wins.

3
JavaScript: the parser-blocker

A <script> tag stops HTML parsing until it downloads and runs — because JS can rewrite the DOM (document.write). defer = download in parallel, run after parsing. async = run as soon as downloaded, order not guaranteed. That's why scripts traditionally go at the bottom.

4
Render tree

DOM + CSSOM merged. Only nodes that show up: anything with display:none is left out (a head element, hidden elements).

5
Layout → paint → composite

Layout (aka reflow) computes the exact geometry — where every box goes, how big it is. Paint fills in pixels. Composite stacks the layers in the right order. Then you see the page.

Bonus points interviewers love

  • Reflow costs more than repaint. Changing geometry (width, position, a div appearing) forces layout again — often for neighbors too. Changing only color or background skips layout and just repaints. Cheapest change: one the browser doesn't have to redo.
  • Shrink the critical path to get first paint faster: inline the CSS you need immediately, defer the JS you don't, and keep the HTML itself small. Fewer blocking resources = earlier paint.
  • Subresources replay lesson 1. Every image, stylesheet, script and font in the HTML fires its own HTTP request. One on a different origin redoes DNS + TCP + TLS from scratch — which is why CDNs and connection reuse matter.

The real skill: say it out loud

  1. "Walk me through what the browser does after it receives the HTML." — 45 seconds, bytes to pixels.
  2. "Why does CSS block rendering — and what does defer do for scripts?"
Model answers (peek only after trying)

Bytes to pixels: "The browser parses the HTML into the DOM — incrementally, as bytes arrive — and parses CSS into the CSSOM. It merges the two into the render tree, which only contains visible nodes. Then layout computes the exact position and size of every element, paint fills in pixels, and compositing stacks the layers. That sequence is the critical rendering path, and the page appears as soon as it completes."

CSS blocking + defer: "CSS is render-blocking because the browser refuses to paint without styles — painting unstyled content and redrawing it later is worse than waiting for the CSSOM. Scripts are different but worse: a plain script tag halts the HTML parser itself, because the script might rewrite the DOM. The defer attribute fixes that: the script downloads in parallel and executes only after parsing finishes, so it never blocks page construction."
