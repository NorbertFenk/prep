Performance: caching, compression, and where the milliseconds go

You now know the whole journey — DNS, TCP, TLS, HTTP, rendering. Every one of those steps costs time, and interviewers love the follow-up: "the page is slow — where would you look, and what would you do?" The answer is a short mental model: find where the time goes, then apply three levers — fewer bytes, fewer round trips, don't repeat work.

Where the milliseconds go

DNS lookup ~20–120 ms (skipped when cached)
TCP handshake 1 RTT
TLS handshake 1–2 RTT (TLS 1.3: 1)
request → wait = TTFB (time to first byte: network + server thinking)
download bytes ÷ bandwidth
parse + render lesson 0006

Notice the pattern: latency dominates, not bandwidth. Every handshake is a round trip bounded by the speed of light — a bigger pipe doesn't make a packet arrive sooner. So the wins come from removing round trips and bytes, not buying more bandwidth.

Lever 1: caching — skip the whole journey

The fastest request is the one never sent. HTTP caching is a contract in the response headers:

HeaderWhat it means
Cache-Control: max-age=3600Fresh for an hour — the browser uses its copy without contacting anyone.
ETag + If-None-MatchRevalidation: "has it changed?" If not, the server answers 304 Not Modified — headers only, no body.
Cache-Control: no-storeNever cache (bank statements, personal data).

CDNs are the same idea at the network level: copies of your assets cached at edges near users, so the round trip is short even on a cache miss.

Lever 2: compression — shrink the bytes

Text is full of repetition, so lossless compression (Content-Encoding: br or gzip) typically shrinks HTML/CSS/JS by 70–80%, negotiated automatically in the request's Accept-Encoding header. Rules of thumb: compress text, pick the right image format (WebP/AVIF over JPEG/PNG, sized to how it's displayed), and don't bother re-compressing things that are already compressed (JPEG, video, WOFF2 fonts).

Lever 3: fewer round trips

ProblemFix
Re-fetching unchanged assetsCache-Control + ETag
Too many bytesCompression, minification, right image formats
Handshake per requestkeep-alive / HTTP/2 one connection, TLS session resumption
Requests queueing behind each otherHTTP/2 multiplexing over one connection
Server far awayCDN edge

Bonus points interviewers love

  • Measure before optimizing. The resource waterfall (devtools Network tab) shows every request as a bar — DNS, handshake, TTFB, download — so you see which lever actually matters.
  • Web Vitals vocabulary: FCP (first contentful paint), LCP (largest contentful paint), CLS (layout shift) — Google uses them, and naming them signals you've done this for real.
  • Static assets get long max-age + versioned filenames (app.a1b2c3.js): cache forever, deploy a new name, zero revalidation traffic.

Check yourself

1. What's the fastest way for the browser to get an asset?

2. A response says Cache-Control: max-age=3600. What does that mean?

3. On reload the server answers 304 Not Modified. What crossed the wire?

4. Why does gzip/brotli shrink HTML and JS by ~70% but barely touch a JPEG?

5. A page served across continents is slow. What's usually the dominant cost?

The real skill: say it out loud

  1. "A user says your site is slow. Walk me through how you'd diagnose and fix it." — 45 seconds.
  2. "How does browser caching work?"
Model answers (peek only after trying)

Slow site: "First I'd measure, not guess — open the network waterfall and see where time goes: DNS and handshakes, time to first byte, or downloading big resources. Then I pull the three levers. Fewer bytes: compression for text, right formats and sizes for images. Fewer round trips: connection reuse, HTTP/2 multiplexing, a CDN so the server is close. And don't repeat work: Cache-Control for freshness, ETags for cheap revalidation, so repeat visits barely touch the network. Latency usually dominates bandwidth, so removing round trips beats shrinking files once the basics are done."

Browser caching: "Caching is a contract set by response headers. Cache-Control max-age says how long a copy stays fresh — while fresh, the browser serves itself and sends nothing. Once stale, it revalidates: it sends the ETag it stored via If-None-Match, and the server either returns the new body or just 304 Not Modified — headers only, the cached body stays valid. Sensitive data gets no-store. CDNs apply the same idea between data centers and users."
