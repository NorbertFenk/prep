HTTP/2 and QUIC: how the journey got faster

Lesson 0010 · How the Internet Works · ~15 min · builds on lessons 0003–0007

Your 60-second answer describes the classic journey. Strong interviewers follow it with: "nice — now, how has that journey been optimized?" Two answers, at two different layers: HTTP/2 fixed the application layer, and when it hit a wall, QUIC rebuilt the transport.

What HTTP/1.1 got wrong

1
One response at a time per connection

A connection could deliver only one response before the next request queued. Browsers coped by opening up to six parallel connections per site — meaning six TCP handshakes and six TLS handshakes, all expensive.

2
Head-of-line blocking (the HTTP kind)

On any single connection, one slow response held up every request behind it — first in line blocks the queue.

3
Crippling header repetition

Every request re-sent full plain-text headers — typically 500–800 bytes, more with cookies (hpbn.co). Ten assets = the same cookie ten times.

HTTP/2 (2015): one pipe, many streams

The core move is a binary framing layer: each HTTP message is split into small binary frames, each tagged with a stream ID. Frames from many requests/responses interleave on one TCP connection, then reassemble at the far end. Methods, status codes, and headers are unchanged — only the wire encoding changed (hpbn.co ch. 12).

HTTP/1.1: conn1 [A......] conn2 [B.....] ...up to 6 conns, 12 handshakes
HTTP/2  : one conn [s1|s3|s1|s2|s3|s1] — frames interleave, tags reassemble them
  • Multiplexing kills response queuing — requests dispatch the moment they're discovered.
  • HPACK compresses headers: repeated fields become tiny table indexes.
  • Prioritization tells the server CSS should beat that hero image.
The catch interviewers probe: did HTTP/2 kill head-of-line blocking?

Only the HTTP-level kind. All streams share one ordered TCP byte stream — so one lost packet stalls every stream while TCP retransmits. On lossy links this can hurt HTTP/2 more than six loss-isolated HTTP/1.1 connections (hpbn.co). Removing one bottleneck revealed the next one: TCP itself.

QUIC → HTTP/3: fixing the transport itself

You can't patch TCP: it lives in operating-system kernels and middleboxes that have ossified around it. So QUIC rebuilds a reliable, secure transport on top of UDP, in userspace, where browsers and servers can actually ship updates (Cloudflare):

  • No cross-stream blocking: streams are independent — a lost packet stalls only its own stream.
  • Fused handshake: transport + TLS 1.3 crypto in one round trip; returning visitors get 0-RTT — data flies in the very first packet burst.
  • Encrypted by default, including most header metadata — there is no plaintext QUIC.
  • Connection migration: identified by a connection ID, not your IP:port pair — switch Wi-Fi → cellular mid-download and the stream survives.

Browsers discover HTTP/3 via the Alt-Svc header and fall back to HTTP/2 gracefully. Check yours right now at cloudflare-quic.com.

Model answers (peek only after trying)

HTTP/2 vs 1.1: "HTTP/1.1 allowed one response per connection, so browsers ran six parallel connections with six sets of TCP and TLS handshakes, and still suffered queuing. HTTP/2 added a binary framing layer that splits messages into stream-tagged frames multiplexed over one connection, compressed redundant headers with HPACK, and added prioritization. But it kept TCP underneath — so one lost packet still stalls all streams. It fixed head-of-line blocking at the HTTP layer, not the transport layer."

Why UDP: "TCP can't evolve — it's frozen into kernels and middleboxes everywhere. QUIC reimplements reliable streams over UDP in userspace, so improvements ship with the browser. That buys independent streams with no cross-stream blocking, a single fused handshake — or zero round trips on repeat visits — mandatory encryption, and connection IDs that survive network switches like Wi-Fi to cellular."
