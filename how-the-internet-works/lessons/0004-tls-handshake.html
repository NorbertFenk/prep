TLS: the handshake that turns TCP into HTTPS

Last chapter your browser finished the TCP handshake with port 443. The connection is open — and completely readable by anyone on the path. TLS fixes three things: encryption (nobody can read it), integrity (nobody can tamper undetected), and authentication (you're really talking to Google, not a wifi snooper impersonating them). The interview core: how does the handshake deliver all three?

~15 min · builds on lesson 0001 step 4 and lesson 0003

Two cryptosystems, one trick

Asymmetric (public/private key)Symmetric (shared secret)
Speedslow (~1000× slower)fast — used for all the data
Key problempublish half, guard halfhow do two strangers share a secret on an open wire?
Role in TLSbootstrap: prove identity + agree a keycarry the actual HTTP traffic

The handshake exists to solve exactly this: use slow asymmetric crypto for a few packets to establish a fast symmetric session key, then switch.

The handshake, step by step

client → server : ClientHello (TLS versions + cipher suites I support)
server → client : ServerHello + Certificate (chosen cipher + proof of identity)
client : verify cert, do key exchange
both : derive the same session key
client ↔ server : Finished (encrypted from here on)
1
ClientHello

"I speak TLS 1.2 and 1.3, here are my supported cipher suites." Also carries random bytes used later in key derivation.

2
ServerHello + Certificate

Server picks the cipher (TLS 1.3 usually) and sends its certificate chain: its domain name, its public key, signed by a CA.

3
Certificate verification

The client checks: signature chains up to a root CA already in my trust store? Domain matches the one I'm visiting? Not expired or revoked? Any failure → full-page warning.

4
Key exchange

Using Diffie-Hellman math, both sides compute the same session key — without ever transmitting it. An eavesdropper sees everything except the key itself (forward secrecy).

5
Finished

Both sides send a MAC of the whole handshake. If a man-in-the-middle altered anything earlier, the hashes mismatch and the connection dies. Then encrypted application data flows.

Bonus points interviewers love

  • TLS 1.3 = one fewer round trip. TLS 1.2 needs 2-RTT before data; 1.3 needs 1-RTT, and 0-RTT if you've connected before. Milliseconds matter.
  • SNI: during ClientHello the client names which hostname it wants — that's how one server serves many HTTPS domains.
  • Session resumption: cached session tickets skip most of the handshake next visit.

The real skill: say it out loud

  1. "What happens during a TLS handshake?" — 45 seconds, cover all three guarantees.
  2. "Why do we need certificate authorities?"
Model answers (peek only after trying)

TLS handshake: "After TCP connects, the client sends ClientHello with supported TLS versions and ciphers. The server picks one and sends its certificate — its public key signed by a CA. The client verifies the chain up to a trusted root, checks hostname and expiry. Then they do a Diffie-Hellman key exchange to agree on a symmetric session key without ever sending it. Finished messages confirm nothing was tampered with, and from there all traffic is encrypted with the fast shared key."

Why CAs: "Two strangers on an open network have no way to know each other's keys are genuine — an attacker can hand you their own key and claim it's google.com's. CAs break that circle: my browser already trusts ~150 root CAs, so a certificate those roots vouch for is proof the key belongs to the domain. Trust gets bootstrapped instead of assumed."
